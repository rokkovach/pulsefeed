Implement the authenticated PulseFeed application using Python 3.11, FastAPI, Jinja2, Tailwind, and focused JavaScript modules for interactions and IndexedDB. Cover the application portions of FR1–FR14; the worker agents own inference implementation. The unused HTMX dependency was removed during the optimization pass.

Own **`app/**` only**, including `app/tests/`, `app/Dockerfile`, `app/railway.json`, `app/pyproject.toml`, templates/static assets, database initialization, environment example, and app README. Use a Python package named `pulsefeed` within this directory.

Other agents work concurrently. Do not edit worker directories, shared schemas, root documentation, or other agents' files. Request shared changes through the coordinator.

Keep durable usage/accounting after view expiry; no saved-feed picker/history. Existing deployment/process/database constraints remain.

2. **Visitor sessions and admin exchange — FR1, FR11.** Default to public home access with isolated visitor cookies/owners; retain API session/CSRF/ownership/global limits. Implement the `/admin` password form and compatible configured root-query bearer exchange into a fresh one-hour admin session with owner preservation, clean 303, cookie flags and rotation/removal revocation. Bare admin flags remain presentation-only. Follow the detailed configuration/security/release section below; legacy CLI access is limited to explicit private mode with no environment admin token.

3. **View RSS — FR2, FR7.** The home page contains only the centered RSS URL form and **View RSS** action, with no saved-feed picker or reader history. Clicking View RSS keeps the home form visible while the server fetches and validates the RSS/Atom response. The reserved inline status shows “Checking feed…” and the URL field is locked during the request. Only an accepted response with a validated reader URL and a durably saved result navigates directly to `/feeds/{view_id}`. Invalid, unsafe, oversized or empty feeds remain on the home form with the entered URL and a bounded error beneath the input. A ten-minute, account-scoped sessionStorage record holds the URL, idempotency key, creation time and submission state, plus a validated result or allowlisted rejection code; it contains no credentials. The posting state is verified before the authenticated POST. Reload never automatically submits or opens an old result: an uncertain request requires an explicit same-key retry, and a completed request can be opened explicitly without another POST. Verified reader arrival consumes its matching completed record so Load a new feed returns to a blank form. Correcting a definitively rejected URL creates a fresh request key. The error area reserves its space so messages do not move the form or footer. Blocked browser storage fails before submission. `/feeds/new` remains a read-only compatibility shell for requests already in progress; new form submissions do not navigate through it. A visitor-session-authenticated, CSRF-protected `POST /api/view-feed` with `{url, idempotency_key}` creates a random, owner-scoped `/feeds/{view_id}` reader page containing a frozen snapshot of at most the first ten source-order articles. `expires_at` is immutable `created_at + 3600 seconds`. Each fresh explicit view, including the same RSS URL with a fresh key, selects the largest affordable source-order prefix up to the configured per-page story cap (default 10, integer 1–10). Selection is atomic under the remaining global daily FLUX-attempt budget, account hourly attempt budget and global hourly start budget; each selected story reserves two FLUX attempts, including retry capacity. The story cap applies independently to each new page; a repeated URL has no separate shrinking daily allowance. Prior views do not suppress fresh runs. Never backfill or drain another batch automatically after admission; an existing view and its request-key replay retain their original selection. Busy/quota-blocked views show a clear no-illustrations notice and a link to the source website. Preserve existing SSRF/DNS/redirect/connection, response-size, XML and HTML defenses. Article content remains source content; page reads never refetch/admit work.

4. **Atomic admission — FR3, FR13, FR14.** Admit the largest affordable source-order prefix up to the current 1–10-story page cap per new view, not lifetime article deduplication. Persist exact request-key replay atomically. Check global capacity, rolling-hour starts, account limits and the shared global daily allowance and per-page story cap in one SQLite transaction on all admission routes. Reserve two FLUX attempts per new image, reconcile known actual attempts and hold uncertain reservations. Distinct fresh views may repeat the same articles but cannot oversubscribe. Generation-only rejection still returns readable `blocked` views.

5. **Coordinator — FR4–FR6, FR8, FR12.** Persist invocations before submission and save provider IDs. Reconcile existing jobs after restart. Store Qwen output/usage, compose and filter the final prompt, validate fallback configuration, and snapshot settings. Require valid FLUX output before completion. Retry safe reads only; do not automatically resubmit inference. Surface uncertain acceptance. Explicit image retries create linked attempts using the saved prompt. At deadline, stop stage advancement, request cancellation, and retain capacity until terminal confirmation or operator resolution.

6. **Browser experience — FR7, FR9, FR10.** Render home form only and `/feeds/{view_id}` image-first cards with square images above text and AI labels. Only selected illustration slots appear; no unselected text-only articles. Failed/unavailable reader images become compact recovery notices. Use friendly UTC dates, linked source websites and a primary **Read original story** CTA; remove image-download functionality. No saved-feed/history picker. Logo and Load a new feed return home. Validate RSS on the home form before navigation, then use a terminal-typed playful loader on the reader while generation and visible image retrieval are pending. Reveal articles after `min(3, selected card count)` actual browser image decodes, with a fade scaled to 12% of observed load time and bounded to 350–1,600 ms. Provider completion or Blob retrieval alone does not count. Apply the reveal once per feed entry; later cards keep their own placeholders and fill without restarting it. Cached refresh counts decoded restored images without extra inference. Browser persistence may finish after an image is displayable. Errors release recovery controls immediately and reduced motion skips cosmetic delays. The background grid uses subtle ambient waves without cursor tracking, synchronized with the floating icon and wind on a shared 8-second cycle. Keep blurred articles on an opaque canvas above the grid, with the spinner overlaid so it leaves no large empty gap. Put the feed name, linked URL, creation time and concise details in a compact header card. Remove standalone RSS Comments boilerplate from displayed excerpts; preserve ordinary prose. CTA buttons use a small keyboard-style press effect. Keep loader/card geometry fixed; ordinary reader hides technical controls. Store image Blobs in IndexedDB under account:view:run keys with the immutable view expiry. Restore only within a valid view. Delete expired view images and revoke their object URLs while the app is running; if the browser was closed, purge expired entries before reading/reusing them on the next visit. Keep theme preferences and authentication intact. The reader has no image-download action. Provider-result availability may end earlier; storage/retrieval failures never trigger automatic inference. A reader view is accessible only to its authenticated owner while unexpired. Missing, foreign and expired view pages return the same generic funny 404 without leaking which condition applied. Reader item, image, batch/status and retry/regeneration calls must all validate unexpired view membership as well as session, ownership and CSRF where applicable. Expiry prevents further reader access/admission but does not erase durable usage/quota history or prematurely release active/uncertain reservations.

7. **Admin view and delivery — FR10, FR11.** Keep `?admin` and `?admin=1` as actual-admin-only settings/per-article controls on the admin's own unexpired reader view. Keep technical details on the reader and a clear Admin dashboard link. Put prompt editing on `/admin` in separate Qwen, FLUX and content-filter forms, each with its own save button. Add `/admin` and `/api/admin/usage` for privacy-limited all-visitor aggregates and shared allowance controls, as specified below. An admin without the query flag receives the normal minimal reader; non-admin admin requests receive 403. All edits/resets require backend role checks and CSRF. Use public visitor sessions by default, the configured admin credential exchange, and no account signup.

Qwen settings show editable system instructions separately from an article-message layout with movable `{{article_title}}` and `{{article_excerpt}}` chips and a live composition preview. Require both markers exactly once and at most 2,000 static Unicode characters. Render field values as JSON-quoted data only in the user message; no recursive interpolation. Default to the current title/excerpt JSON layout. New settings affect future runs, preserving historical snapshots, prepared requests and saved image-retry prompts. The FLUX editor retains its independent `{{qwen_prompt}}` token.

## Admission limits and aggregate administration

`POST /api/admin/limits` accepts exactly `{global_daily_limit, feed_article_limit}`: the global daily attempt limit is an integer 1–10,000 and the per-new-page story cap is an integer 1–10. `GET /api/admin/usage` reports the cap as `quotas.page: {article_limit, max_articles: 10}`; there is no per-URL daily allowance. `GLOBAL_DAILY_IMAGE_LIMIT=100` and `FEED_ARTICLE_LIMIT=10` only seed a missing SQLite policy; admin edits remain authoritative. Migration replaces the obsolete feed-daily policy without deleting historical usage, global charges or active/uncertain reservations. Changing the cap affects only new pages; it never changes an existing view’s selection.

Initialize the SQLite-authoritative policy to **100 FLUX attempts/day globally** across all visitors and a separate **10-story cap per new page**, editable from 1–10. A repeated URL has no independent daily allowance. The day boundary is **00:00 UTC**. These are additive to the existing 30 attempts/account/hour and five generation/retry submissions/account/minute. Every allowance check/edit/reset is transactionally consistent; do not use process-local or per-account copies of the shared policy.

Add `GLOBAL_HOURLY_GENERATION_LIMIT` with default **30 accepted per-article generation starts in a rolling 60-minute window across all visitors**. Count admission once, independently of eventual outcome, including Qwen failure before FLUX; no refund on failure, no extra start for same-key replay/status reads, and no multiplication by internal worker retries. Enforce it atomically in SQLite on every generation/retry admission alongside five submissions/minute/account, 30 image attempts/hour/account, the shared 100 FLUX attempts/day global budget and the per-new-page story cap (default 10). Expose the global rolling-hour usage read-only to actual admins; editing limits does not clear it. Explicit Reset allowances clears spent global rolling-hour starts and visitor hourly attempts as well as daily charges, while preserving active/uncertain reservations and all model history. This is an application limiter, with no new worker hourly limiter. Automatic midnight rollover affects only the daily budget; explicit Reset allowances also clears spent hourly budgets. Immutable admission epochs prevent late settlement from restoring pre-reset starts. Recent active/unknown starts remain counted until completion or rolling-hour expiry; daily and visitor image reservations stay held regardless of age.

Apply the current story cap independently to each fresh page, including repeated URLs. Keep existing view selections frozen after policy changes; never backfill or automatically admit later articles. Persist reservation/settlement links so retries, late results, restart, and midnight cannot double-charge or lose reservations. Reusing existing work reserves nothing new. Reconcile zero attempts only when that zero is known; uncertainty retains the full reservation.

Provide actual-admin-only limit editing/reset controls and show **used, reserved, remaining, next reset time**. Reset changes allowance accounting, not model-usage history or audit history. Preserve in-flight and uncertain reservations on reset and UTC rollover. Lowering a limit blocks new work without cancelling admitted work or making remaining allowance negative in the UI. Explicit reset clears spent account/hour attempts too; it never clears submission/minute or other request throttles. Preserve an internal audit record of edits/resets.

## Public access and Railway admin configuration

`PUBLIC_ACCESS_ENABLED=true` is the default: a fresh external browser opens the home form directly, without signup, CLI seeding or an access link. The server issues an isolated anonymous visitor session/cookie and owner identity. Every reader API still requires that session, CSRF for mutations, owner/unexpired-view membership, and all existing global/account limits. Public reading never grants admin access or exposes another visitor's view.

Open `/admin` (also linked from the reader footer) to sign in with the admin password stored in `ADMIN_ACCESS_TOKEN`. The password travels only in a bounded POST form, protected by an expiring signed cookie/nonce, same-origin validation and the existing IP attempt limit. Successful sign-in preserves the visitor owner and rotates into the existing expiring admin session. Failed sign-in does not echo the password or change visitor ownership. Login forms use a same-origin referrer policy for native form compatibility; private credential links and other pages retain no-referrer. Existing configured private links remain compatible.

The admin dashboard is ordered as Usage overview, Prompt settings, Limits, then separate Qwen and FLUX usage reports. Reset allowance is an action inside Usage overview with inline confirmation, not a separate collapsible section. Prompt editing lives on `/admin` in separate collapsible Qwen, FLUX and content-filter sections, each with its own save button and feedback. Qwen uses one prompt editor with an explicit `--- ARTICLE CONTEXT ---` divider: system instructions above, article layout below. Article title/excerpt tokens stay movable; Add-token buttons appear only for missing tokens. The two roles remain separate in the saved API fields and worker messages. FLUX retains the movable Qwen token. The content section saves blocked terms and the fallback prompt together. Each `POST /api/admin/settings/{section}` accepts only that section’s fields, requires admin authority and CSRF, uses the shared admin write limit, and merges atomically with current settings. Saving one section never submits or overwrites another section’s unsaved draft. Qwen/content saves preserve an existing legacy FLUX prefix; only an explicit FLUX save migrates its template. Changes affect future runs, preserving saved run settings.

Configure `ADMIN_ACCESS_PARAM=admin_key` (a safe ASCII identifier), a long random URL-safe `ADMIN_ACCESS_TOKEN` in server environment/secrets, and `ADMIN_SESSION_SECONDS=3600`. Opening the root URL `/?<configured-param>=<private-token>` validates the bearer credential, issues a fresh HttpOnly/SameSite=Lax session cookie (Secure in production), and returns `303` to clean `/admin`. If a visitor session already exists, preserve its owner and view ownership while elevating only the session; never make that visitor identity globally admin. Keep the credential out of navigation, bootstrap JSON, page content and subsequent URLs. The configured credential is reusable until rotated or removed. Rotation/removal revokes derived sessions; restoring an earlier token does not revive those revoked sessions. Bare `?admin`/`?admin=1` remains only a protected presentation toggle and cannot authenticate an admin.

Configure variables in the Railway service's Variables settings and deploy the staged changes. Seal `ADMIN_ACCESS_TOKEN`, `SESSION_SECRET` and `RUNPOD_API_KEY`; keep endpoint IDs/configuration as appropriate non-secret variables. Set `APP_BASE_URL` to the exact public HTTPS origin, `COOKIE_SECURE=true`, and retain one replica/ASGI process/coordinator plus the `/data` volume and SQLite database. This is setup guidance, not evidence that variables or cloud resources have been provisioned. [Railway variables](https://docs.railway.com/variables)

The admin link is a bearer URL. Its credential can appear in browser history or ingress/proxy logs; a clean redirect cannot promise zero leakage. Application access logging is disabled and exchange responses use `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; also redact the credential query parameter from upstream/edge logging and tracing before external release. Keep links out of screenshots, shared logs and documentation. Verify the deployed proxy/logging configuration rather than assuming the app controls upstream retention.

Legacy CLI-issued private access is compatibility-only: enable it with `PUBLIC_ACCESS_ENABLED=false` and no configured `ADMIN_ACCESS_TOKEN`.
